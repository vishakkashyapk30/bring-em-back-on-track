# What changed from the design phase, and why

The build-phase rules allow changing the design if the README says what changed and why. This is the full list. The root README has a summary.

**Baseline:** the design-phase submission, [`design/system_design_files/collections_system_design_V1.md`](design/system_design_files/collections_system_design_V1.md) (V1) and its shorter version v2. **Drivers of change:** the [critique](reviews/system_design_critique.md), the [build-phase instructions](brief/build_phase_instructions.md), and practical constraints (36 hours, solo, no LLM budget). Decision IDs (Dn) are the numbers of the build plan's decisions.

Status: **Decided** = agreed and in the plan. **Built** = implemented in the repo. **Planned** = scheduled, not built yet.

| # | Area | Design phase said | Build does | Why | Status |
|---|---|---|---|---|---|
| 1 | Layer 4 scope | Three use cases: NBA, post-call summary, agent assist (V1 also adds 15 novel capabilities) | **One use case, Next Best Action.** Post-call summary and agent assist are supporting services inside the NBA workspace. The summary feeds approved text features into NBA (D1) | The brief asks for one use case; the critique flagged scope | Decided |
| 2 | NBA framing | Risk model + ladder, uplift in Phase 2 | Stated explicitly: Phase 1 is a **rule-based treatment ladder informed by a break-risk model**, not causal optimisation (D2) | Break risk is not treatment effect; honest framing | Decided |
| 3 | Allocation objective | break chance × amount at risk − contact cost | Expected cure benefit with a **capped** amount at risk, minus contact cost and a complaint penalty (D3) | Aligns the objective with the 30-day cure KPI instead of dollars | Planned |
| 4 | Identity resolution | Exact keys → Splink → LLM reads masked pair, steward decides | Deterministic bridges → **scored matching** (Fellegi-Sunter-style weights checked on deterministic links: 99.96% precision) → steward review queue; no LLM in the matching path (D4) | LLM verdicts are hard to validate; a false merge is the worst error | Built |
| 5 | NL-to-SQL security | Semantic-layer allowlist + sqlglot checker | **Read-only connection, table allowlist (no CRM customer table), personal-detail columns blocked, role views in gold**; sqlglot is defence in depth (D5) | A parser miss can't expose personal data | Built |
| 6 | LLM provider | Claude via API on synthetic data; bank-hosted in production | **Provider-agnostic, three tiers**: a paid API (OpenAI or Anthropic, Gemini and DeepSeek also supported), then a local Ollama model, then deterministic rules, which are the default offline and always answer (D13) | The brief allows paid APIs; the demo must still work with no network or key | Built (providers, fallback chain, offline provider) |
| 7 | Frontend | Streamlit | **React + Vite + TypeScript + Tailwind**, inspired by a Figma community file and themed in CIBC colours (D7) | Approve/override flows, role-based navigation, a polished demo | Built (skeleton on fixtures) |
| 8 | Operational writes | DuckDB has one writer, so approvals go to a side file merged nightly | **SQLite (WAL) `ops.db`** for approvals, overrides, summaries, hardship events and an **append-only audit log** (enforced by triggers) (D8) | Real-time writes for the demo; nightly merge contradicted the < 5 min re-score | Built |
| 9 | Fairness gate | Drop or coarsen any feature group with proxy AUC > 0.65 | **Above 0.65 the group is dropped from the model input automatically (training excludes it and the report says so) and is also sent to a person for review with the numbers**; under the line it stays. **Outcome tests** by group (action, contact and cure rates, calibration, error rates, overrides) still go to review, not to an automatic drop (D10) | The design says drop or coarsen; a drop is the safe default and a person confirms it. Outcome gaps need judgement, so they only go to review | Built (no group is above 0.65 on the real data, so nothing is dropped today) |
| 10 | Hardship latch | Raise to possible, specialist confirms, a person lowers with a reason | Same, plus a **review deadline** for `possible` (default 5 business days, TBC) with escalation to the team lead (D11) | An unresolved `possible` shouldn't persist indefinitely | Latch rules built; deadline planned |
| 11 | RAG | Current versions only; no citation, no answer | Plus **precedence for conflicting documents** (policy > regulatory summary > programme terms > procedure > call script > FAQ; the regulatory summary itself defers to the policy) and a coverage check (D12) | Critique: conflicting current documents weren't handled | Built |
| 12 | Model evaluation | AUC vs the bank's v2.1 | AUC **plus** calibration, precision/recall at the top decile, lift, backtested cure impact (D15) | Capacity is limited, so ranking quality at the top matters | Planned |
| 13 | Data contract | 10 quality rules | Adds **rule 11: no customer-facing decision may use a feature older than its freshness SLA**. Will be aligned with the release's example contract **DC-COLL-001** | Critique recommendation; build-phase instruction | Draft built |
| 14 | Hand labels | ~200 identity pairs, 200 hardship snippets, 30 RAG answers, all by hand | Hardship and text-feature evaluation uses the **release's 500 public labels each for notes and transcripts**; identity pairs and RAG answers still by hand | The release provides labels; saves about 1.5 hours | Decided |
| 15 | Benchmark | Organisers' benchmark with tolerance + rubric | Also scored against the release's **dev answers**; submitted in the official CSV format (`question_id, answer, sql_or_sources, refused`), generated by the system, never edited by hand | Build-phase instruction | Built |
| 16 | Deployment | Laptop (DuckDB, Streamlit); production stack named | **Docker Compose modular monolith**: `web` (nginx), `api` (all layers in one process), `jobs` (batch, run to completion); optional `worker` and `ollama`. **No microservices** (D17) | Reproducible demo with no host setup; splitting adds hops with no benefit at this scale | Built |
| 17 | Warehouse refresh | Nightly gold rebuild | Built into a separate file, contract-tested, then **atomically swapped in**; the API picks it up without a restart | DuckDB single-writer rule; "a failed test blocks publish" | Built |
| 18 | Testing | Contract tests, benchmark | Plus an **independent spec test suite** written by a separate agent that saw only the brief and design docs (unit, integration and system tests against an adapter interface) (D18) | Catches drift between the build and the spec | Written; binding planned |
| 19 | Hosting | Not in scope | Optional **Render Blueprint** (free plans) for a hosted demo on fixtures or a small demo warehouse | Shareable demo link | Written, not deployed |
| 20 | Headline novel capability | Choose in hour 3 between S1 (employer shock radar) and H1 (plan simulator) | **H1 plan simulator** with H2 review board and H3 missed offers. S1 not built | Profiling found no employer or regional cluster for the ECO-0715 layoffs (Windsor-Essex manufacturing payroll delay 7.3% vs 7.8% elsewhere); H1 is fully supported, including card programs and 0% rate overrides. See [`profiling_decisions.md`](profiling/profiling_decisions.md) | Decided |
| 21 | Identity bridges | Exact keys, then Splink | Exact keys plus a **majority vote over the CRM IDs in account snapshots** (fixes ~2.6% mistyped IDs, links 99.8% of snapshotted accounts) and **CIF normalisation** (156,837 CIFs lost leading zeros) before Splink | Found in profiling | Decided |
| 22 | Business value | ~2,800 cases a month, CAD 0.7M a year | ~14,400 cases a month in 2026, ~CAD 2.1M a year for +2 points of 30-day cure (to be refined on matured cohorts) | Real volumes | Decided |
| 23 | Ask (Layer 2) | Claude parses questions to tokens, MetricFlow compiles, LanceDB RAG | **Offline semantic compiler** (certified metrics, dimensions, filters, time phrases mapped from the question, compiled to one SELECT), **BM25 retrieval** over current policy sections with precedence and a coverage check, rule-based call summaries | Reproducible, auditable answers by default (an LLM now sits on top, see row 6); 19-document corpus doesn't need a vector store. Dev benchmark 0.994 ([`ask.md`](reference/ask.md)) | Built |
| 24 | Text features (Layer 3) | LLM extraction, checked on 200 hand labels | **Rule extractor mined from and measured on the release's 500 public labels** each for transcripts and notes (99.6% hardship accuracy on transcripts, 98% exact summaries; 95% on notes) | Release provides labels; offline and reproducible | Built |
| 25 | Feature definitions | Same dbt code for offline and online | **One dbt macro evaluated as of the promise's creation (training) and as of now (live)**; parity check recomputes 1,000 online rows (0 mismatches) | Makes "one definition" literal and testable | Built |
| 26 | Golden ID format | `G-NNNNNN`, stable via overlap with the previous run | `G-` + the cluster's smallest CRM ID (e.g. `G-KIW6380`) | Stable across reruns without storing previous runs; readable | Built |
| 27 | Collections links | coll_customer_ref is the CRM ID | ~2.8% of cases (and their contacts, notes, promises, transcripts) carry a mistyped CRM ID; they are linked through the case's primary account | Found during identity resolution | Built |
| 28 | Weather map (S2) | Bubbles by FSA, groups under 10 hidden | Built on real data: broken-promise or hardship rate per FSA centroid, one sequential hue + size = customers, 21 small areas suppressed; replaces the employer radar in the app | S1 had no signal; S2 is the analyst view the data supports | Built |
| 29 | Cure rate definition | 30-day cure, cohort-based | Follows the release's certified `metric_definitions.cure_rate` default filter: insolvency and deceased holds excluded | Certified definitions win; found by the independent spec suite | Built |

| 31 | Unsourced policy questions | No citation, no answer | Question words the documents never use count against coverage, so off-topic policy questions (e.g. pet insurance) are refused instead of answered from the nearest section | Found by the independent spec suite | Built |
| 32 | One-command start | `make up` + `make nightly` | `docker compose up --build`: a bootstrap container fetches the dataset if missing and builds the warehouse once; Docker and local runs share `./data` (no duplicate warehouse) | Single command for judges; disk | Built |

## Open spec questions found during the build

The independent spec suite's review raised five questions (meaning of "clear", Sunday contact, the definition of pressure actions, the treatment ladder order, and who may change the hardship flag or run the simulator). All five are settled in [`profiling_decisions.md`](profiling/profiling_decisions.md) §3.
